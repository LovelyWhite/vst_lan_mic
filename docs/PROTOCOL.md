# 网络协议与线程设计

## 协议版本

唯一的 C++ 协议定义位于 `common/Protocol.h`。固件和插件直接使用同一文件；
`esp32s3/include/Protocol.h` 仅为转发头。Python 发现工具按相同格式读取。

当前版本为 **6**，不兼容版本 5。使用时必须一起更新固件与两个插件。
版本 6 保留电脑到 ESP32 的 14 ms PCM，上行每包 672 样本；ESP32 到电脑改为
20 ms 裸 Opus 包，以降低 lwIP/Wi-Fi TX 的持续负载。Opus 固定为 48 kHz、
单声道、192 kbps CBR、音乐模式，不使用 Ogg 容器。

## 数据报

所有多字节字段都显式按小端读写，不直接发送 C++ 结构体，不依赖结构体对齐或主机字节序。
固定包头 28 字节。PCM 音频包共 1372 字节；加上 UDP/IPv4 头共 1400 字节，
低于 1500 MTU，不需要 IP 分片。Opus payload 为 1 至 512 字节，192 kbps CBR
的 20 ms 音频通常为 480 字节。

| 偏移 | 字节 | 字段 | 说明 |
| --- | --- | --- | --- |
| 0 | 4 | magic | `0x31534f53`，线上字节为 `SOS1` |
| 4 | 1 | version | `6` |
| 5 | 1 | kind | 1 Discover、2 Offer、3 Subscribe、4 Ack、5 Audio、6 AudioOpus |
| 6 | 2 | flags | Sender=1、Receiver=2、Busy=`0x8000` |
| 8 | 4 | session | 非零会话 ID，Discover 可为零 |
| 12 | 4 | sequence | 每个音频方向独立的包序号，允许自然回绕 |
| 16 | 4 | timestampMs | 发送端单调毫秒计数，允许自然回绕 |
| 20 | 4 | sampleRate | 必须是 48000 |
| 24 | 2 | payloadBytes | 必须与实际 UDP 长度完全匹配 |
| 26 | 2 | reserved | 必须为零 |
| 28 | 可变 | payload | 控制信息、PCM16 或裸 Opus packet |

Audio 仅用于电脑到 ESP32，必须 flags=0、payloadBytes=1344，即 672 个单声道
有符号 16 位样本。AudioOpus 仅用于 ESP32 到电脑，必须 flags=0，
payloadBytes 为 1 至 512；每包解码为 960 个单声道样本。
Offer 必须 flags=0，负载为 1 至 64 字节 ASCII 设备身份，不带终止符。
Discover、Subscribe、Ack 无负载。接收方拒绝错误版本、采样率、长度、保留字段或类型。

## 发现与订阅

1. 固件监听 UDP 45678（控制）和 45679（上行音频）。
2. 每个插件绑定自己的主临时端口，并为每个有效 IPv4 接口绑定独立的临时发现
   socket，在尚未选中设备时每秒从各接口广播 Discover。设备选中后停止广播和
   网卡端点重建，仅保留单播订阅续约；租约失效后立即恢复发现。Windows 上
   JUCE 8.0.6 无法提供接口定向广播地址，因此各绑定 socket 发送 limited
   broadcast，避免 VPN、虚拟网卡或多网卡让发现包只从错误接口发出。
3. 固件单播 Offer 回请求来源端口，payload 为 `vst_lan_mic-<eFuse MAC>`，session 为本次开机随机 ID。
4. 插件自动选择最先发现的设备，或选择用户指定身份。DHCP 地址不保存在工程中。
5. 插件每秒向选中设备 45678 发送 Subscribe，flags 为 Sender 或 Receiver，session 为插件实例随机 ID。
6. 固件每方向独立维护 `源 IP + 源端口 + 插件 session` 租约。未占用或原持有者续约时返回 Ack；冲突时 Ack 追加 Busy。
7. 租约自最后一次成功 Subscribe 起 3500 ms 失效。关闭插件或禁用网络后自然超时，不发送广播注销。
8. 固件和插件都识别开机会话变化，重新发现和订阅。多实例不会共用一个电脑固定接收端口。

Sender 向固件 45679 发送音频，session 使用自己的实例 ID，且源端口必须与订阅相同。
Receiver 通过订阅登记接收端口。固件从 45679 向该端口单播音频，session 使用固件开机 ID。
旧的固定电脑下行端口 45680 不再使用。接收插件单独启动也可以获取手机音频，不依赖发送插件。

每台设备同时最多服务一个 Sender 和一个 Receiver。默认自动选择不会遇到 Busy 就抢占或切换其他设备，
避免发送、接收插件无意中连到不同手机；用户可在界面显式选择。

随机 session 用来隔离重启和实例，不是身份认证或安全令牌。

## 音频与缓冲

- VST 插件接受 DAW 当前工程采样率：发送插件流式转换到网络 48 kHz，接收插件
  将网络 48 kHz 转回 DAW 采样率。重采样相位跨 DAW block 连续，不要求 block
  大小是网络帧整数倍。
- DAW 位深不由 VST 插件控制；宿主提供的浮点样本只在网络发送边界饱和量化为
  PCM16，接收方向则将解码后的 PCM16 转回宿主浮点样本。
- USB 提供双通道 48 kHz / 16 bit；手机播放左右平均为网络单声道，上行单声道复制到 USB 左右通道。
- USB UAC2 Feature Unit 1 的播放音量和静音请求在手机播放（USB OUT）下混前处理；
  `-100..0 dB` 控制值转换为对应的振幅增益，而不是直接使用归一化控制位置。
  左右通道使用独立原子定点目标和约 5 ms 平滑，避免控制回调持锁或音量阶跃爆音。
  Feature Unit 2 的麦克风控制不会改动该增益。库内建 `volume_active` 保持关闭，
  因为它处理的是相反的 USB IN 麦克风方向。
- USB IN 端点描述符预留 49 个样本的最大包，但运行时包长控制在 48 kHz 下
  每 1 ms 发送 48 个立体声样本，即 192 字节。不能固定发送 196 字节，
  否则实际消费速率会变成 49 kHz 并周期耗空网络播放队列。
- 网络消费者按递增序号接收，丢弃重复包及迟到包。没有额外的乱序等待窗口。
- 电脑到 ESP32 的 1～2 个 PCM 帧短缺口在缺口本身时长内使用平滑曲线淡出到零
  再淡入，避免端点直线插值产生低频爆音，也不会额外修改下一帧；更长缺口最多
  保持 300 ms 时间轴，仍使用淡出、静音和恢复淡入保护。
- ESP32 到电脑的 Opus 缺口调用解码器 PLC，最多补 15 个 20 ms 帧。更大缺口先重置
  解码器，防止旧预测状态和无限追赶；超过补偿上限的时间不会重放。
- ESP32 麦克风接收器和电脑插件接收器均默认积累 14784 样本，即 22 个
  14 ms 等效帧、约 308 ms 后起播。
  空队列后重新起播，并执行短淡入/淡出。
- 根据队列占用，线性插值以最多 ±0.2% 的速率微调补偿 USB 与 DAW 时钟偏差。
  接近目标水位时校正量自动回到零。
- 队列超过目标再加 300 ms 时，消费者裁剪至目标长度；这是异常恢复，可能听到短暂跳变。
- 网络发送队列丢弃本地排队超过 300 ms 的帧，断网时持续排空，不在恢复后重播积压数据。
- ESP32 下行编码为 20 ms / 192 kbps CBR Opus，每轮最多发送一个数据报；发送资源
  暂时不足时丢弃失败帧，并按
  10/20/40/80/100 ms 上限指数退避。恢复时跳过队列旧帧并从最新帧继续，
  由接收端按序号缺口做平滑补偿，避免重试风暴和过期音频。
- VST 上行按绝对 14 ms 截止时间发送；小于一帧的线程调度误差会由后续周期吸收，
  不从实际发送时刻重新计时，避免误差累计后周期性丢帧。
- 500 ms 没有有效音频会清理接收状态；租约超时或设备切换也会清理。
- 时间戳不用于跨设备单向延迟计算，因为两端时钟没有同步。

发送插件始终保留本地原始输出，Network gain 只作用于网络音频；
接收插件的 Network gain 作用于返回音频。编码前 PCM 饱和限制在 16 位范围，
非有限浮点输入按静音处理，避免无效转换。

## 线程所有权

| 线程 | 所有权与职责 |
| --- | --- |
| Arduino TinyUSB 任务 | USB 端点及枚举；由框架创建 |
| 固件 audio，Core 1 | 唯一 USB 流读写调用者；立体声转换；上行缓冲消费；下行帧生产 |
| 固件 network，Core 0 | 唯一 Wi-Fi UDP socket 使用者；发现、租约、序号检查、Opus 编码、收发 |
| DAW 音频线程 | 浮点/PCM 转换、队列生产/消费、增益平滑，无网络调用和互斥锁 |
| 插件 network | 唯一 socket 使用者；发现、续约、Opus 解码与 PLC、收发、重连 |
| JUCE 消息线程 | 界面与设备列表；设备选择使用独立设置锁，不在音频回调中获取 |

`SpscRing` 的读游标只由消费者修改，写游标只由生产者修改，使用 acquire/release 原子发布数据。
清空与裁剪只发生在消费者；网络线程通过 epoch 通知 DAW 清空接收队列，不跨线程重置游标。
电脑插件要求 `std::atomic<uint32_t>` 始终无锁；ESP32 固件不作此编译期要求，
允许 SDK 的原子操作后备实现。`is_always_lock_free == false` 不表示原子操作不可用，
也不改变上述内存序与队列所有权约束。固件不宣称这些操作始终无锁，其时延仍需实机验证。

## 依赖边界

USB 音频类由固定版本 `arduino-audio-tools` 提供，包括描述符、控制请求及传输回调。
固件 Opus 依赖固定为 `codec-opus` 1.6.1，编码器状态当前显式分配到内部 RAM；
桌面插件通过 CMake 获取官方 Xiph Opus 1.6.1 并静态链接。固件需持续监控
内部堆最小值、最大连续块及 UDP 发送失败。
当前 Arduino 3.3.12 提供 `USB_INTERFACE_AUDIO`，固件直接使用该接口槽。
对于较早的 Arduino 2/3 版本，在唯一引入 USB 音频头文件的翻译单元中，
将该名字适配到 `USB_INTERFACE_CUSTOM`。Arduino 2/3 以外的主版本需要重新检查适配。
不修改 PlatformIO 缓存，不重新编译或重复启用 TinyUSB 内置音频类。

本地核对的是源码接口，不是完成了二进制兼容性或手机实测。升级依赖需要重新核对：
USB 类驱动结构、SOF API、等时端点 API、描述符以及跨核缓冲实现。
